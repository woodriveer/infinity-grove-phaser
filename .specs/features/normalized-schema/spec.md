# Normalized Schema Specification

## Problem Statement

The database has no foreign keys: a `username`, `hero_id`, chapter or stage can point to a row that does not exist, and nothing stops it. `stages` repeats eight enemy columns per row (`monster*` and `miniboss*`), and `chapters` repeats four more for the boss, even though the 50 phase monsters share only 5 attribute sets. Copper drops come from a single fixed `app.wallet.drop-table` level in `application.yaml`, so every kill of the campaign pays 1-5 copper whatever the stage. The schema is generated by `ddl-auto: update`, which cannot drop columns, move data or add constraints.

## Goals

- [ ] Every column that names a row of another table is a foreign key, and the database rejects a write that breaks it.
- [ ] Enemy attributes are stored once per distinct set in `enemies`; `stages` and `chapters` reference them.
- [ ] Copper drops are defined per stage and chapter through `drop_rules`; `application.yaml` holds no drop table.
- [ ] Flyway owns the schema and Hibernate only validates it.

## Out of Scope

| Feature | Reason |
| ------- | ------ |
| Keeping existing players, wallets, cards and equipment | User decision: the local database is recreated from the new `V1` migration |
| Card and equipment drop chances per stage | User chose copper only; `app.cards.*` and `app.equipment.*` stay in `application.yaml` |
| Enemy names or art in `enemies` | No feature uses them yet |
| Normalizing `player_cards.cleared_chapters`, `wallet_levels.drops` and `equipment_pieces.affixes` (comma-separated text) | Not raised; they hold no reference to another table |
| Admin UI or API to edit enemies and drop rules | Values are tuned in the database, as today |
| Changing combat, progress or reward rules | Only the storage and the source of drop values change |

| Enemy catalog shape | `enemies(id, element, physical_defense, magical_defense, crit_resistance)` with a unique constraint on the four attributes; health and time limits stay on `stages`/`chapters` | User decision; the unique constraint is what makes identical sets share one row | y |
| Drop rule references | `stages.monster_drop_rule_id`, `stages.miniboss_drop_rule_id`, `chapters.boss_drop_rule_id` → `drop_rules(id)`; one rule may be referenced many times | User decision | y |

| Encounter rule ids in the API | `StageResponse` gains `monsterDropRuleId` and `minibossDropRuleId`; `ChapterResponse` gains `bossDropRuleId` | The game needs the rule of the encounter it shows to pick the queue | n |
| Delete behavior: player-owned rows | FKs from `wallets`, `wallet_drop_queues`, `progress`, `player_cards`, `card_copies`, `equipment_pieces`, `refresh_tokens` to `users(username)` use `ON DELETE CASCADE` | Rows that belong to a player have no meaning without the player | n |
| Delete behavior: catalog references | FKs to `heroes`, `chapters`, `stages`, `enemies` and `drop_rules` use `ON DELETE RESTRICT` | A catalog row in use must not vanish under a player | n |
| Progress reference | `progress(chapter, stage)` → `stages(chapter, number)` | Progress always points at an existing stage of its chapter, the completed state included | n |
| Seeding | Heroes, chapters, enemies and drop rules are seeded at startup by the existing seeders (enemies and drop rules through the chapter seeder), never overwriting rows that exist | Keeps the tuned-in-database behavior of `ChapterSeeder`; the seed rules stay in Kotlin, where they are tested | n |
| Farm fights | Still drop no copper | Today's rule (`ClickerGame` drops coins only outside the farm) | n |
| Tests database | Integration tests run the Flyway migration on the Testcontainers PostgreSQL | The migration is the schema; tests must use it | n |

## User Stories

### P1: Referential integrity ⭐ MVP

**User Story**: As the game operator, I want every reference between tables enforced by the database so that no row can point to a player, hero, chapter, stage, enemy or drop rule that does not exist.

**Why P1**: This is the inconsistency the user reported; the other stories build their tables on top of it.

**Acceptance Criteria**:

1. The system SHALL create the schema only through the Flyway migration `V1__schema.sql`, with Hibernate set to `ddl-auto: validate`.  <!-- ubiquitous -->
2. IF the entities do not match the migrated schema THEN the system SHALL fail to start.  <!-- unwanted -->
3. IF a row of `wallets`, `wallet_drop_queues`, `progress`, `player_cards`, `card_copies`, `equipment_pieces` or `refresh_tokens` is written with a `username` absent from `users` THEN the database SHALL reject the write.  <!-- unwanted -->
4. IF a row of `hero_skills`, `card_copies` or `equipment_pieces` is written with a non-null `hero_id`, or `player_cards` with a `leader_id`, absent from `heroes` THEN the database SHALL reject the write.  <!-- unwanted -->
5. IF a `stages` row is written with a `chapter` absent from `chapters` THEN the database SHALL reject the write.  <!-- unwanted -->
6. IF a `progress` row is written with a `(chapter, stage)` pair absent from `stages` THEN the database SHALL reject the write.  <!-- unwanted -->
7. WHEN a `users` row is deleted THEN the database SHALL delete that player's rows in `wallets`, `wallet_drop_queues`, `progress`, `player_cards`, `card_copies`, `equipment_pieces` and `refresh_tokens`.  <!-- event -->
8. IF a `heroes`, `chapters`, `stages`, `enemies` or `drop_rules` row that another row references is deleted THEN the database SHALL reject the delete.  <!-- unwanted -->
9. WHEN the application starts on an empty database THEN the system SHALL migrate it and seed the 5 chapters, their stages, the hero catalog, the enemies and the 15 drop rules.  <!-- event -->
10. IF a `stages` or `chapters` row is written with an enemy id or drop rule id absent from `enemies` or `drop_rules`, or a `wallet_drop_queues` row with a `drop_rule_id` absent from `drop_rules`, THEN the database SHALL reject the write.  <!-- unwanted -->

**Independent Test**: Integration tests against the migrated Testcontainers PostgreSQL insert an orphan row for each FK and assert the constraint violation, delete a user and assert the cascade, delete a referenced catalog row and assert the rejection.

### P1: Enemy catalog ⭐ MVP

**User Story**: As the game operator, I want each distinct enemy stored once so that tuning an enemy changes one row and `stages` holds no repeated attribute columns.

**Why P1**: The repeated columns the user wants gone.

**Acceptance Criteria**:

1. The system SHALL store element, physical defense, magical defense and crit resistance only in `enemies`; `stages` and `chapters` SHALL have no such columns.  <!-- ubiquitous -->
2. The system SHALL reference the phase monster and the miniboss of a stage through `stages.monster_enemy_id` and `stages.miniboss_enemy_id`, and the chapter boss through `chapters.boss_enemy_id`.  <!-- ubiquitous -->
3. IF two rows of `enemies` are written with the same element, physical defense, magical defense and crit resistance THEN the database SHALL reject the second.  <!-- unwanted -->
4. WHEN the chapters are seeded THEN the system SHALL reuse the existing `enemies` row for an attribute set already stored instead of inserting another.  <!-- event -->
5. WHEN the 5 chapters are seeded on an empty database THEN `enemies` SHALL hold exactly 5 phase-monster rows (one per element with defenses and crit resistance 0) shared by all 50 stages.  <!-- event -->
6. WHEN a chapter is read THEN the system SHALL return the same element, defenses and crit resistance per stage monster, miniboss and boss that `ChapterDefinition.of` produces for that chapter.  <!-- event -->
7. IF an `enemies` row has a defense outside 0..90 or a crit resistance outside 0..100 THEN the database SHALL reject the write.  <!-- unwanted -->

**Independent Test**: Seed an empty database, count `enemies` rows by kind, read each chapter through `GET /progress` and compare every enemy with `ChapterDefinition.of`.

### P1: Drops per stage ⭐ MVP

**User Story**: As the game operator, I want each stage's monster and miniboss, and each chapter's boss, to name the drop rule it pays so that later stages can pay more copper without a config change.

**Why P1**: The user's third request; it removes the fixed drop table from `application.yaml`.

**Acceptance Criteria**:

1. The system SHALL read drop rules only from `drop_rules`; `application.yaml` SHALL contain no `app.wallet.drop-table`.  <!-- ubiquitous -->
2. WHEN the drop rules are seeded THEN chapter `c` SHALL have a monster rule of `c` to `5c` copper, a miniboss rule of `5c` to `15c` copper and a boss rule of `20c` to `50c` copper, each with a 1500 ms kill interval.  <!-- event -->
3. WHEN chapter `c` is seeded THEN every stage SHALL reference chapter `c`'s monster rule as `monster_drop_rule_id` and its miniboss rule as `miniboss_drop_rule_id`, and the chapter SHALL reference its boss rule as `boss_drop_rule_id`.  <!-- event -->
4. IF a `drop_rules` row has `min_copper < 1`, `max_copper < min_copper` or `kill_interval_ms < 1` THEN the database SHALL reject the write.  <!-- unwanted -->
5. WHEN a progress response is returned THEN each stage SHALL carry `monsterDropRuleId` and `minibossDropRuleId` and the chapter SHALL carry `bossDropRuleId`.  <!-- event -->
6. WHEN `GET /wallet` answers THEN `drops` SHALL hold one queue of 20 values per drop rule, keyed by the rule id as a decimal string, every value inside that rule's range.  <!-- event -->
7. WHEN `POST /wallet/sync` receives kills keyed by drop rule id THEN the system SHALL credit them with the same queue and allowance rules that applied per level, using each rule's range and kill interval.  <!-- event -->
8. IF `POST /wallet/sync` names a drop rule id that does not exist THEN the system SHALL answer `400` with code `WALLET_UNKNOWN_DROP_RULE` and credit nothing.  <!-- unwanted -->
9. WHEN a phase monster, miniboss or chapter boss of the campaign dies THEN the game SHALL take the drop from the queue of that encounter's drop rule and report the kill under that rule id.  <!-- event -->
10. WHILE the player fights a farm boss the game SHALL drop no copper.  <!-- state -->
11. IF the queue of the encounter's drop rule is missing or empty THEN the game SHALL drop nothing for that kill.  <!-- unwanted -->

**Independent Test**: In the browser, kill a chapter 1 monster (1-5 copper), its miniboss (5-15) and the chapter boss (20-50), then sync and reload: the wallet matches the backend total.

---

## Edge Cases

- IF a drop rule's range is changed in the database THEN the system SHALL re-roll that rule's queues on the next wallet read, as it does today for a changed level range.
- IF a drop rule is added in the database THEN the system SHALL open a full queue for it in each wallet on the player's next wallet read.
- WHEN the application restarts on a seeded database THEN the seeders SHALL insert nothing and overwrite nothing.

## Success Criteria

- [ ] An orphan insert into any of the 20 referencing columns fails with a foreign-key violation.
- [ ] `stages` has no enemy-attribute column, and `enemies` holds 5 shared phase-monster rows after seeding.
- [ ] A chapter 2 miniboss kill credits 10 to 30 copper, from `drop_rules`, with nothing about drops in `application.yaml`.
